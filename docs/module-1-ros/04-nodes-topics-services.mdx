# ROS 2 Core Concepts - Nodes, Topics, Services

## Introduction

ROS 2 (Robot Operating System 2) is not an operating system but rather a flexible framework for writing robot software. It's a collection of tools, libraries, and conventions that aim to simplify the task of creating complex and robust robot behavior across a heterogeneous cluster of processors. Understanding the core communication patterns in ROS 2 is essential for controlling humanoid robots effectively.

In this chapter, we'll explore the fundamental concepts of ROS 2 communication: nodes, topics, services, and actions. These form the backbone of how different components of a humanoid robot system communicate and coordinate with each other.

## ROS 2 Architecture Overview

### Nodes

A **node** is an executable that uses ROS 2 to communicate with other nodes. In a humanoid robot system, you might have nodes for:
- Joint controllers
- Sensor processing (IMU, cameras, LiDAR)
- Path planning
- Motion planning
- State estimation
- High-level behavior control

Nodes are lightweight processes that can be distributed across multiple machines. They communicate with each other through topics, services, and actions.

### Communication Patterns

ROS 2 provides three main communication patterns:

1. **Topics (Publish/Subscribe)**: Asynchronous, many-to-many communication
2. **Services (Request/Response)**: Synchronous, one-to-one communication
3. **Actions (Goal/Feedback/Result)**: Asynchronous, long-running tasks with feedback

## Topics and Message Passing

### Understanding Topics

Topics are the primary mechanism for asynchronous, one-way communication in ROS 2. Data flows from publishers to subscribers. This pattern is ideal for sensor data, joint states, and other continuous streams of information.

### Creating a Publisher Node

Let's create a simple publisher that could simulate sensor data from a humanoid robot:

```python
# sensor_publisher.py
import rclpy
from rclpy.node import Node
from sensor_msgs.msg import JointState
from std_msgs.msg import Header
import math
import time

class JointStatePublisher(Node):
    def __init__(self):
        super().__init__('joint_state_publisher')

        # Create a publisher for joint states
        self.publisher_ = self.create_publisher(JointState, 'joint_states', 10)

        # Timer to publish data at 50 Hz
        timer_period = 0.02  # seconds
        self.timer = self.create_timer(timer_period, self.timer_callback)

        # Initialize joint names and positions
        self.joint_names = [
            'left_hip_yaw', 'left_hip_pitch', 'left_hip_roll',
            'left_knee', 'left_ankle_pitch', 'left_ankle_roll',
            'right_hip_yaw', 'right_hip_pitch', 'right_hip_roll',
            'right_knee', 'right_ankle_pitch', 'right_ankle_roll',
            'left_shoulder_pitch', 'left_shoulder_yaw', 'left_shoulder_roll',
            'left_elbow', 'left_wrist_pitch', 'left_wrist_yaw',
            'right_shoulder_pitch', 'right_shoulder_yaw', 'right_shoulder_roll',
            'right_elbow', 'right_wrist_pitch', 'right_wrist_yaw'
        ]

        self.i = 0

    def timer_callback(self):
        msg = JointState()
        msg.header = Header()
        msg.header.stamp = self.get_clock().now().to_msg()
        msg.header.frame_id = 'base_link'

        msg.name = self.joint_names
        msg.position = []

        # Generate some example joint positions (oscillating for demo)
        for i, _ in enumerate(self.joint_names):
            # Create a unique oscillation pattern for each joint
            position = math.sin(self.i * 0.01 + i * 0.1) * 0.5
            msg.position.append(position)

        self.publisher_.publish(msg)
        self.i += 1
        self.get_logger().info(f'Publishing joint states: {len(msg.position)} joints')

def main(args=None):
    rclpy.init(args=args)
    joint_state_publisher = JointStatePublisher()

    try:
        rclpy.spin(joint_state_publisher)
    except KeyboardInterrupt:
        pass
    finally:
        joint_state_publisher.destroy_node()
        rclpy.shutdown()

if __name__ == '__main__':
    main()
```

### Creating a Subscriber Node

Now let's create a subscriber that listens to joint states:

```python
# joint_state_subscriber.py
import rclpy
from rclpy.node import Node
from sensor_msgs.msg import JointState

class JointStateSubscriber(Node):
    def __init__(self):
        super().__init__('joint_state_subscriber')
        self.subscription = self.create_subscription(
            JointState,
            'joint_states',
            self.listener_callback,
            10)
        self.subscription  # prevent unused variable warning

    def listener_callback(self, msg):
        # Process the joint states
        self.get_logger().info(f'Received joint states for {len(msg.name)} joints')

        # Example: Check if any joint is at extreme position
        for i, (name, position) in enumerate(zip(msg.name, msg.position)):
            if abs(position) > 1.5:  # Check for extreme position
                self.get_logger().warn(f'Joint {name} at extreme position: {position:.2f}')

def main(args=None):
    rclpy.init(args=args)
    joint_state_subscriber = JointStateSubscriber()

    try:
        rclpy.spin(joint_state_subscriber)
    except KeyboardInterrupt:
        pass
    finally:
        joint_state_subscriber.destroy_node()
        rclpy.shutdown()

if __name__ == '__main__':
    main()
```

## Services for Request/Response Communication

Services provide synchronous, request/response communication. They're ideal for operations that have a clear beginning and end, like setting a robot's pose or requesting sensor calibration.

### Creating a Service Server

```python
# pose_service_server.py
import rclpy
from rclpy.node import Node
from geometry_msgs.msg import Pose
from your_robot_interfaces.srv import SetRobotPose  # Custom service

class PoseServiceServer(Node):
    def __init__(self):
        super().__init__('pose_service_server')
        self.srv = self.create_service(
            SetRobotPose,
            'set_robot_pose',
            self.set_pose_callback
        )

        # Current robot pose
        self.current_pose = Pose()

    def set_pose_callback(self, request, response):
        self.get_logger().info(f'Setting robot pose to: x={request.target_pose.position.x}, y={request.target_pose.position.y}')

        # In a real robot, this would send commands to actuators
        self.current_pose = request.target_pose

        # Simulate some processing time
        import time
        time.sleep(0.1)  # Simulate movement time

        # Set response
        response.success = True
        response.message = f'Pose set successfully to x={request.target_pose.position.x}, y={request.target_pose.position.y}'
        response.final_pose = self.current_pose

        return response

def main(args=None):
    rclpy.init(args=args)
    pose_service_server = PoseServiceServer()

    try:
        rclpy.spin(pose_service_server)
    except KeyboardInterrupt:
        pass
    finally:
        pose_service_server.destroy_node()
        rclpy.shutdown()

if __name__ == '__main__':
    main()
```

### Creating a Service Client

```python
# pose_service_client.py
import rclpy
from rclpy.node import Node
from geometry_msgs.msg import Pose, Point, Quaternion
from your_robot_interfaces.srv import SetRobotPose

class PoseServiceClient(Node):
    def __init__(self):
        super().__init__('pose_service_client')
        self.cli = self.create_client(SetRobotPose, 'set_robot_pose')
        while not self.cli.wait_for_service(timeout_sec=1.0):
            self.get_logger().info('Service not available, waiting again...')

        self.req = SetRobotPose.Request()

    def send_request(self, x, y, z=0.0):
        self.req.target_pose.position = Point(x=x, y=y, z=z)
        self.req.target_pose.orientation = Quaternion(x=0.0, y=0.0, z=0.0, w=1.0)

        self.future = self.cli.call_async(self.req)
        rclpy.spin_until_future_complete(self, self.future)

        return self.future.result()

def main(args=None):
    rclpy.init(args=args)
    pose_service_client = PoseServiceClient()

    # Send a request to move to a specific position
    response = pose_service_client.send_request(1.0, 2.0)

    if response:
        pose_service_client.get_logger().info(f'Response: {response.message}')
    else:
        pose_service_client.get_logger().error('Service call failed')

    pose_service_client.destroy_node()
    rclpy.shutdown()

if __name__ == '__main__':
    main()
```

## Actions for Long-Running Tasks

Actions are used for long-running tasks that require feedback and the ability to cancel. They're perfect for humanoid robot tasks like walking, grasping, or path following.

### Creating an Action Server

```python
# walk_action_server.py
import rclpy
from rclpy.action import ActionServer
from rclpy.node import Node
from your_robot_interfaces.action import WalkToGoal  # Custom action
from geometry_msgs.msg import Point
import time

class WalkActionServer(Node):
    def __init__(self):
        super().__init__('walk_action_server')
        self._action_server = ActionServer(
            self,
            WalkToGoal,
            'walk_to_goal',
            self.execute_callback)

    def execute_callback(self, goal_handle):
        self.get_logger().info('Executing walk to goal...')

        target_x = goal_handle.request.target_pose.position.x
        target_y = goal_handle.request.target_pose.position.y

        # Simulate walking progress
        for i in range(101):  # 0 to 100 percent
            if goal_handle.is_cancel_requested:
                goal_handle.canceled()
                self.get_logger().info('Walk goal canceled')
                return WalkToGoal.Result()

            # Publish feedback
            feedback_msg = WalkToGoal.Feedback()
            feedback_msg.current_position = Point(x=target_x * i/100, y=target_y * i/100, z=0.0)
            feedback_msg.progress = float(i)
            goal_handle.publish_feedback(feedback_msg)

            self.get_logger().info(f'Walking progress: {i}%')
            time.sleep(0.05)  # Simulate walking time

        # Complete the goal
        goal_handle.succeed()
        result = WalkToGoal.Result()
        result.success = True
        result.final_position = Point(x=target_x, y=target_y, z=0.0)

        self.get_logger().info(f'Walk completed to ({target_x}, {target_y})')
        return result

def main(args=None):
    rclpy.init(args=args)
    walk_action_server = WalkActionServer()

    try:
        rclpy.spin(walk_action_server)
    except KeyboardInterrupt:
        pass
    finally:
        walk_action_server.destroy_node()
        rclpy.shutdown()

if __name__ == '__main__':
    main()
```

### Creating an Action Client

```python
# walk_action_client.py
import rclpy
from rclpy.action import ActionClient
from rclpy.node import Node
from your_robot_interfaces.action import WalkToGoal
from geometry_msgs.msg import Point

class WalkActionClient(Node):
    def __init__(self):
        super().__init__('walk_action_client')
        self._action_client = ActionClient(self, WalkToGoal, 'walk_to_goal')

    def send_goal(self, x, y):
        goal_msg = WalkToGoal.Goal()
        goal_msg.target_pose.position = Point(x=x, y=y, z=0.0)

        self._action_client.wait_for_server()

        self._send_goal_future = self._action_client.send_goal_async(
            goal_msg,
            feedback_callback=self.feedback_callback)

        self._send_goal_future.add_done_callback(self.goal_response_callback)

    def goal_response_callback(self, future):
        goal_handle = future.result()
        if not goal_handle.accepted:
            self.get_logger().info('Goal rejected :(')
            return

        self.get_logger().info('Goal accepted :)')

        self._get_result_future = goal_handle.get_result_async()
        self._get_result_future.add_done_callback(self.get_result_callback)

    def feedback_callback(self, feedback_msg):
        feedback = feedback_msg.feedback
        self.get_logger().info(f'Received feedback: {feedback.progress:.1f}% complete')

    def get_result_callback(self, future):
        result = future.result().result
        self.get_logger().info(f'Result: {result.success}')
        rclpy.shutdown()

def main(args=None):
    rclpy.init(args=args)
    action_client = WalkActionClient()

    action_client.send_goal(5.0, 3.0)

    try:
        rclpy.spin(action_client)
    except KeyboardInterrupt:
        pass
    finally:
        action_client.destroy_node()

if __name__ == '__main__':
    main()
```

## Advanced Communication Patterns

### Using Quality of Service (QoS) Settings

For humanoid robots, you may need different QoS settings based on the type of data:

```python
from rclpy.qos import QoSProfile, QoSReliabilityPolicy, QoSHistoryPolicy

# For critical control commands
control_qos = QoSProfile(
    depth=1,
    reliability=QoSReliabilityPolicy.RELIABLE,
    history=QoSHistoryPolicy.KEEP_LAST
)

# For sensor data where latest is most important
sensor_qos = QoSProfile(
    depth=5,
    reliability=QoSReliabilityPolicy.BEST_EFFORT,
    history=QoSHistoryPolicy.KEEP_LAST
)

# Publisher with specific QoS
self.control_publisher = self.create_publisher(
    JointCommand,
    'joint_commands',
    control_qos
)
```

## Debugging ROS 2 Communication

### Using Command Line Tools

ROS 2 provides several command-line tools for debugging:

```bash
# List all available topics
ros2 topic list

# Echo messages from a topic
ros2 topic echo /joint_states

# List all available services
ros2 service list

# Call a service
ros2 service call /set_robot_pose your_robot_interfaces/srv/SetRobotPose "{target_pose: {position: {x: 1.0, y: 2.0, z: 0.0}}}"

# List all available actions
ros2 action list

# Get information about a specific topic
ros2 topic info /joint_states
```

## Best Practices for Humanoid Robot Communication

### 1. Message Design

Design your messages efficiently:
- Use appropriate data types (float32 vs float64)
- Group related data in single messages when appropriate
- Consider bandwidth limitations for wireless communication

### 2. Topic Organization

Structure your topics logically:
- `/robot_name/sensor_type/data` (e.g., `/humanoid1/imu/data`)
- `/robot_name/component/command` (e.g., `/humanoid1/left_arm/command`)
- `/robot_name/component/state` (e.g., `/humanoid1/joint_states`)

### 3. Error Handling

Always implement proper error handling:

```python
def listener_callback(self, msg):
    try:
        # Process the message
        self.process_joint_data(msg)
    except Exception as e:
        self.get_logger().error(f'Error processing joint data: {e}')
        # Implement fallback behavior
        self.fallback_safety_procedure()
```

### 4. Performance Considerations

For humanoid robots with many joints:
- Use appropriate publishing rates (not too fast, not too slow)
- Consider message compression for large data
- Use latching for static transforms
